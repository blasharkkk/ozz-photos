# Ozz photos

一片悬在破碎镜面上方的纸照片云。照片像棉纸一样挂在细线上漂浮，底下是破碎的镜面，
天花板投下摇曳的光斑。纯 WebGL2 手写渲染，无框架、无构建步骤。

## 在线体验

- 公网：https://paper-cloud.app.workbuddy.host/
- 本地运行：任意静态服务器，例如 `python -m http.server 8123`，然后打开 `http://127.0.0.1:8123/index.html`

## 特性

**3D 场景**
- 拖动环视、滚轮/双指缩放、**远距点照片飞入聚焦、已放大居中后再次单击翻面看背面**、方向键切换、Esc 退回全景
- 鼠标掠过照片与丝线会有柔和的力场扰动；按住照片可下拉牵引，松手弹簧回弹
- 聚焦时其余纸片柔和淡出，贴近视线才碎成纸屑
- 纸片沿法线做抛物面微卷曲（`curl`）。⚠️ **归一化基准必须用半高的平方**：
  早先写成 `aB.x*aB.x`（半宽的平方），而照片按比例生成、`w ≠ h` 是常态，
  基准错了会让曲率随宽度线性放大 —— 纸片正对镜头时整张扭曲成梯形，
  用户实测「刚加的照片整个变形，翻转一下才正常」。
  现为 `curl * (q.x²/aB.x² - .25)`，且幅度 `∝ min(aB.y²,.3)*.55`（与纸片尺寸成比例，
  否则小纸片被卷没、大纸片纹丝不动），法线也同步 `normalize` 修正

**照片编辑器（放进云之前）**
- 自由裁剪 + 常用比例锁定（1:1、4:3、3:4、3:2、2:3、16:9、9:16）
- **面板高度固定（`height: min(760px,100%)` + `box-sizing:border-box`），切横/竖屏界面纹丝不动**
  - ⚠️ 早先面板高度是**内容撑出来的**，而裁剪图 `max-height:56vh`、预览 `max-height:44vh`
    都随照片比例变化 → 裁成竖屏后两列同时变高、面板从 577px 撑到 726px，整套界面跟着长高。
    现在：面板定高 → `.ed-body` 用 `flex:1;min-height:0` 吃掉剩余 → 裁剪台高度有
    200px～52vh 的上下限、预览区 `flex:1` 且 `max-height:54%`，两者都**只改自身不改列高**
  - ⚠️ 两列必须**硬绑定 `.ed-body` 的高度**：`.ed-left/.ed-right` 同时写
    `align-self:stretch` **和** `height:100%`，并各自 `min-height:0`；`.ed-left` 另加
    `overflow:hidden`。只写 `stretch` 是不够的——拖裁剪手柄把照片压成细长条时，
    预览画布变成 20×520 的细长图，右列被内容撑到 792px（body 仅 634px），
    `stretch` 反而跟着长，面板 `scrollHeight 896 > 756` 直接溢出视口（用户实机复现）。
    `height:100%` 的百分比只在父高确定时才解析，正好锁住这一点
  - ⚠️ **窄屏媒体查询里必须显式解除**：`height:auto; align-self:auto`。
    否则 `height:100%` 会让手机端左列吃掉全部高度、右列（预览/相纸/相框）整列消失
    ——而只量面板高度的测试抓不到它，要用**可见面积**断言
- **裁剪框把手不得溢出裁剪台**（`tools/test-crop-handles.js`，8 用例 5 断言）
  - ⚠️ 把手偏移**不能是负值**。早先是 `left/top/right/bottom:-7px`：15px 的方块（含 1px border）
    以框边为圆心向外探出 7px，而 `.ed-stage` 有 `overflow:hidden` → 裁剪框贴到舞台边缘时
    （`crop.top` 最小 35px），上下两排把手各被切掉 5~8px，只剩 7px 可点，拖到边缘"抓不住"
    （实测 `stage.scrollHeight 334 → 342`，底部 `se/s/sw` 底边 342.8 >舞台 335.8）。
    现改为 **偏移 0**：把手完整落在框内，永远不会被裁切
  - 配套 `CROPPAD = 7`（`main.js`）：框贴图片边时留 7px 余量，让 13px 的把手始终有一半压在图片内。
    **`clampCrop` 与 `moveCrop` 必须用同一套边距**，否则缩放时框会"跳"到图片最边上、把手跑到框外
  - ⚠️ 余量**不能跟着框宽缩小**（如 `Math.min(CROPPAD, c.w/3)`）：框被压到 8px 时余量退化成 2.7px，
    装不下 13px 把手 → 右列把手又跑出舞台（实测 `crop R12.3` < `stage 536`）。
    正确做法：余量恒为 `CROPPAD`，同时把框宽一起夹到 `2×CROPPAD` 以内
- **完成/取消挂在标题行右端**（`.ed-head > .ed-headrow > .ed-headbtns`）
  - ⚠️ 早先这个按钮组的容器 `.ed-foot` 被写在了 `.ed-body` **内部**。而 `.ed-body` 是
    `flex-wrap:wrap` 的弹性容器 → 按钮组被当成"第三列"挤到右列右边（实测 x=895,w=156），
    右列上方空出一大块。现在容器已从 `.ed-body` 移出，挂在标题行里。
- 相框：**只有下边可调**（3%~30%），上/左/右三边固定 7% 不动；另有「等边」「无相框」
  - 语义迁移：旧存档的 `fw` 是三边宽，按 2.2 倍折算成下边宽，老照片重新编辑后外观不变
- 新添加的照片固定落在**视平线附近（y≈2.4）**，不再随机到接近天花板——
  `addPhoto` 结尾会聚焦新照片，位置过高时画面就成了"照片死贴着天花板"
- **新添加照片的挂高随机 + 空位优先**（`tools/test-photo-height.js`，9 项）
  - ⚠️ 曾经的 bug 是 `addPhoto` 里**硬编码 `s.y = 2.4`** → 每张新照片都挂在同一水平线，
    用户实测：「每次新加的照片都是在同一高度，距离天花板的高度一致」
  - 当时的动机是"随机到 4.55 会让照片死贴天花板"—— 但那是把
    **「别贴天花板」误当成「钉死一个高度」**来解决的，矫枉过正
  - 现在把高度区间**作为参数传进 `makeSheet`**：`makeSheet(pi, false, [1.6, 4.0])`。
    ⚠️ **区间必须传进候选搜索内部，不能选完再把 y 夹回来** ——
    「空位优先」是按候选 y 算出来的距离，后夹会把最空的位置破坏掉
  - 上限 4.0：房间高 `RH=5.4`，纸片半高约 .4 → 顶边约 4.4，留 1.0 余量不贴天花板
  - 实测 10 张：高度 1.79~3.86（跨度 2.07），10 个不同值，两两最小间距 0.841
  - 回归还守着「不贴天花板」「不低于 1.0」两条边界 —— 这正是当年钉 2.4 的初衷，不能丢
- **用户照片纸片的尺寸维持原区间**（`tools/test-photo-size.js`，9 项）
  - ⚠️ **别再为了"更有随机性"放宽尺寸**：v106 曾把高度从 .55~.80 放宽到 .40~1.00、
    宽度上限提到 1.05 → 用户实测反馈**「有的照片大的吓人了」**（云里已有 30 张示例照片，
    再放大镜般的新照片会压住整片云）。**v107 已按用户要求还原**
  - 用户真正要的是**挂高随机**（与天花板的距离），不是尺寸放大，见上一条
  - 该测试断言「尺寸落在原有区间内」，**不是**「尺寸差异要大」——别再改回去
- 相纸系统：
  - **纯色** —— 11 种预选色排两行，第二行末尾是调色球（conic 彩虹 + 原生取色器），与背面画笔的颜色球同一套
  - **涂鸦** —— 38 种手绘图形，相框锁死为窄边/等边/宽边三套固定模板
  - **镭射** —— 6 张全息箔（银虹/香槟金/玄黑/青蓝/玫粉/墨绿），**正面与背面都随角度流光**：
    - 片元着色器用 `dot(N,V)`（视线与纸面法线夹角）驱动薄膜干涉相位，再叠一条随时间流动的高光带
    - ⚠️ 条件里**不能只判正面**：早先写成 `if (holo && front)`，背面就整片漏掉、仍是烘焙的静态渐变
    - **背面整张都是相纸**（无照片窗口），所以窗口遮罩只在正面生效；条纹用 `buv`（背面可能被镜像）以免拉花
    - **背面同样铺满整张箔面**：镭射纸即使没在背面画过任何东西，也会生成背面贴图
      （`needBack = paper.holo || 画过东西`），否则翻到背面是一块空白
    - 实例缓冲每张 24 float，**槽位顺序必须与 attrib() 字节偏移严格一一对应**：
      `0-3` 中心xyz+yaw ｜ `4-7` 宽高相位层 ｜ `8-11` 裁切uv ｜ `12-15` 动力学(位移xyz+偏航) ｜
      `16-19` 镭射强度+种子+左右窗口 ｜ `20-23` 上下窗口+背面宽高比+底色亮度
    - **写实要点（用户拿真实镭射箔参考图纠正后的四条，务必保持）**：
      1. **底色必须是金属灰/深色**，虹彩是「叠加在底上的光」而非把底染成粉彩。
         旧色板底色用粉彩（`#f3cfd8`/`#d9f0d2`）→ 满屏艳丽、很假。
      2. **虹彩要低饱和**：`0.5+0.5·cos()` 是数学上的满饱和色环，必然经过纯品红/纯黄/纯青。
         现在生成后向亮度靠拢（`mix(vec3(lum), irid, .42)`）得到粉彩「闪色」。
      3. **要有磨砂颗粒**：真箔面不是镜面平滑，而是极细的磨砂颗粒（近看闪成细密微光）。
         纯色渐变看起来就是塑料。`laserFoil` 末尾按像素加确定性哈希噪声。
      4. **光栅微纹用 soft-light、强度收窄**：`grate*(1+bright*3)` 在浅底上放大 4 倍会叠出艳丽花纹。
    - **纹理必须「不规则」**（用户实测「玄黑纹理很生硬、能看到明显痕迹」）：
      真实箔面的衍射是细密多频的，早先用了**等间距直线光栅**（`per` 固定、`lineWidth = 0.9×per`）
      + 着色器里**单频正弦** `sin(uv*320)`，深底改加法混合后这些规则条纹被照亮 →
      屏幕上出现极其明显的横条，像印刷痕迹。现改为：
      - 烘焙层：间距**随机抖动**（`jit = per*(1.3+rnd*1.5)`）、线宽仅 0.3×per、alpha 封顶 .1
      - 着色器：两个**不可通约频率**相乘（`sin(uv*197+…)*sin(uv*89-…)`）+ `normalize` 法线
      - 干涉相位：`film` 噪声频率从 `vec2(5,3.4)` 提到 `vec2(14,9.5)` 并叠一层更细的
        （低频噪声只会让色带平滑地弯几下，反而显得是「画上去的渐变」）
    - **六张必须「一眼能分辨」**：靠底色的**色相 + 明度档位**拉开，不是都做成灰银色。
      现行分档：银虹/香槟金（最亮）→ 玫粉（偏暗玫瑰）→ 青蓝/墨绿（中档冷色）→ 玄黑（最暗）。
      实测留白区明度 247 / 245 / 214 / 226 / 202 / 52，任意两张综合距离 > 40。
    - **深底（玄黑）必须用加法混合 `plus-lighter`，不能用 `screen`**：
      screen 的公式是 `1-(1-a)(1-b)`，**底色越暗提升越明显** —— 黑底(0.08) 叠一层 alpha .3 的色带
      直接变 0.36（灰），黑镭射被冲成「灰白」。改加法后实测背面明度 47.6、饱和 0.178。
      同时深底的色带要**窄而稀疏**（条数 ×0.55、alpha ×0.34）——黑纸上只该偶尔泛出一道光。
    - **虹彩强度要按底色深度调制**（`vPaper2.w` = 该纸底色相对亮度）：
      `depthMul = 0.38 + lum*0.82`，且 `amt` 硬封顶 0.55、`mix` 封顶 0.8。
      否则纸片侧转时 `ang→1`，深底玄黑会被整片虹彩盖住（用户实测「背面满屏彩虹、黑镭射都不黑了」）。
    - **背面不能沿用正面的「朝灰度压 85%」**：那是为了模拟颜料渗进棉纸，
      但背面整张是箔面，压灰会把虹彩差异削到只剩 15% —— 这正是「正面有流光、背面没有」的原因。
      背面改为只轻微提亮、不压灰。
    - ⚠️ **`laserFoil` 里 `bright` 曾一直算错**：`parseInt(c.slice(1), 16)` 把 `'141418'` 当十六进制
      解析成 1315864，导致 `bright` 恒等于 1 ——「按底色亮度自适应」的**所有分支从来没生效过**，
      玄黑一直被当浅底处理。现改为解析 r/g/b 三分量求亮度。**改动任何按亮度分支的逻辑前，
      先用 `node -e` 单独验证 `bright` 的取值。**
      - ⚠️ 曾把相纸数据误写进 `12-15`，纸片动态位移读到「镭射强度1 / 种子数千」，
        表现为**照片被甩飞 + 吊线拉成满屏斜线且静止后一直定住**；种子还串到下一张纸的 x/y。
        这类错误**不报错、只静默错乱**，所以留了 `window.__sheetSlots()` 供测试逐槽核对
    - 背面贴图是长方形而纹理数组是正方形 `LAYER×LAYER`：上传时按该照片自己的
      `paper.aspect` 做**等比居中 contain**，着色器用同一映射（`vPaper2.z`）取样，图案才不变形
    - `laserFoil()` 自绘完整个纸面后返回 `null`，`paintPaper` 据此跳过二次 `fillRect`——
      否则那次重刷会用上一个渐变抹掉全部 screen/overlay 纹理（浅色系最明显，玄黑看不出来）
  - **DIY**（原「自制」，按用户要求改名）—— 上传**已扣好镂空的相纸底图**（PNG，透明处即照片窗口），采用**图层套叠**：

- **相纸层渲染缓存**（`paperLayerWarm`）：`laserFoil` 要画色带 + 光栅 + 上万个颗粒点，
  单张约 30ms（平板 60~90ms），而点色卡就触发一次 → 用户实测「平板端按钮响应很慢」。
  解决：① 按 key 缓存已渲染的相纸层（同 key 直接贴图）② 切到镭射系列后用空闲时间
  **预热六张**（每张之间让出一帧，UI 不卡）。实测点击耗时 **24ms → 1.6ms**。
  - ⚠️ key 必须由 `paperLayerKey()` 统一生成（预热与实际取缓存共用），
    否则两处算法漂移会永远命中不了（我踩过：`custom` 只有纯色才该进 key、
    `side/bottom` 要 `toFixed(3)`，都曾导致预热白做）
  - 换 DIY 底图 / 从 localStorage 恢复底图时必须 `paperLayerCache = null`（key 里只有 'upload'）

**⚠️ 移动端「按钮触摸无反应」的第一嫌疑：祖先节点的 `touchstart`/`touchmove` + `preventDefault`**
- 症状：桌面端点击正常，**手机/平板上某些按钮点了没反应**（v108 用户实测：完成/取消/背面创作）。
- 根因：`preventDefault()` 在 `touchstart`（或首个 `touchmove`）上会**掐掉浏览器合成的 `click`**。
  若祖先节点（如编辑器根）对一片区域统一 `preventDefault` 去"防整页拖动"，会把里面按钮的 click 一起杀掉。
- 修法：拦截时排除可点击元素 ——
  `if (closest(区域) && !closest('button,a,input,select,textarea,label,[role="button"]')) preventDefault();`
  CSS 的 `touch-action:none` 已兜底整页拖动，空白区即便不 JS 拦截也安全。
- 测法：用**触摸事件路径**测，不能只靠 mouse。见 `tools/test-touch-buttons.js`
  （页面内合成 `TouchEvent` 读 `defaultPrevented` + 真实 CDP 触摸点按验证）。

- 症状：**刷新/重开页面后，用户自己加的照片全部消失**，回到 6/30 张示例
- 根因：`var DB_NAME = 'paper-cloud', STORE = 'kv'` 声明在文件**下方**（约 3350 行），
  而启动时（约 326 行）就调用了 `storeGet`。`var` 只提升声明、**赋值语句尚未执行**，
  于是启动那一刻 `DB_NAME`/`STORE` 都是 `undefined` → `indexedDB.open(undefined)` 打开一个
  叫 "undefined" 的假数据库并抛错 → **启动读取必然失败**
- 为什么一直没被发现：`storeGet` 里 `catch` 吞掉了这个错，然后 fallback 去读 localStorage，
  而 `storeSet` 又把整份照片镜像了一份到 localStorage —— **兜底掩盖了致命 bug**。
  一旦去掉兜底（v113 同时做的），病根立刻暴露：连续 4 次刷新全部只读到示例照片
- 修法：常量**上移到启动读取之前**用 `const` 声明；localStorage 照片镜像彻底移除，
  IndexedDB 成为唯一真相来源
- 教训：**任何在模块顶层就被调用的函数，其依赖的常量必须在它之前完成初始化**；
  `var` 的提升只提升声明不提升赋值，跨"顶层 await 调用"时极易踩坑
- ⚠️ 因为这条以前从未被测过，才潜伏至今——**"刷新后数据还在"必须作为回归项**（现已固化为测试）

## 技术要点

- 纯 WebGL2 + GLSL，无任何运行时依赖
- 照片存进 `TEXTURE_2D_ARRAY`，正反两层纹理按纸片朝向采样
- 每张照片用**独立确定性随机种子**决定位置与取景，给某张照片加背面/裁剪都不会扰动其它照片
- 翻转 180° 后需水平镜像 UV，背面文字才正向可读；背面朝外的纸片不镜像（用 per-instance 标记区分）
